Scope VCS · implementation plan · run detail v2

Make every failure explain itself.

Replace the monolithic run log with durable, per-attempt step executions and a shareable run-detail route. Retries remain attempts of the same run, presented as a simple newest-first list without user-facing attempt numbers.

Recommended implementation

Keep one sequential container job per attempt. Persist every workflow step under that attempt, make the runner report explicit step transitions, tag logs with their step, and render attempts from most recent to oldest. The stored attempt ordinal remains an internal invariant only.

01

Product contract

This work answers “what happened?” without broadening the workflow language. The hierarchy is run → attempts → sequential step executions → logs.

Attempt presentation

Render attempts in descending created_at_unix order. The newest row is expanded by default. Do not render “Attempt 1,” “Attempt 2,” an ordinal badge, or a total attempt count.

Internal ordinal

Retain the persisted attempt number for uniqueness, transition validation, and runner recovery. It must not cross into user-facing copy or accessibility labels.

Step identity

A step execution is identified by attempt ID plus zero-based workflow step index. Its name and command come from the run’s immutable workflow revision, avoiding duplicated definitions.

Retry meaning

“Run again” adds a fresh attempt to the same run and preserves older attempts. It does not create a synthetic new workflow or rerun a single step. Bound each run to 100 durable attempts so the complete detail response and browser projection remain finite; the limit stays out of ordinary UI copy and the retry action disappears when exhausted.

Refresh behavior

Keep the existing fixed two-second model. Poll run metadata while the detail route is mounted and request only logs newer than the selected step’s cursor.

Authorization

Preserve repository membership enforcement, private source boundaries, log limits, immutable image pinning, and the existing cancel/retry permissions.

Pre-materialized steps

Claiming creates all pending step records from the pinned workflow revision in the same transaction.

Ordered execution

A step may start only when every earlier step succeeded and no later step has started.

Aggregate conclusion

Final-step success succeeds the attempt; step failure fails it and skips all remaining pending steps.

Typed terminal reason

Distinguish step failure, timeout, cancellation, runner loss, and runner setup failure.

Immutable definition

Names and commands are read from the workflow revision already retained for the run.

Retry isolation

Every retry receives fresh step rows. Completed older attempts are never mutated.

05

Sequential lifecycle

The server validates every transition. The runner observes execution, but it cannot skip ahead or declare an aggregate result that disagrees with the persisted steps.

06

Runner protocol V3

Replace one opaque job script with explicit step transitions. Reuse one container and workspace, restarting the container for each step so Docker owns the authoritative exit result.

One container

Checkout and workspace initialization happen once. Files created by a step remain available to later steps.

Fresh step shell

Each command starts from /workspace in a fresh fail-fast sh -e; shell-local cd and exports do not leak forward.

Control journal

A runner-owned journal records the selected step, phase, and start nonce. Step programs are mounted read-only, Docker records the exit status, and user log text is never parsed as control state.

Start gate

The container completes runner-owned setup and publishes its nonce, then waits. The runner durably starts that step through the API before atomically releasing user code, so setup failures remain setup failures without allowing execution ahead of server state.

Recovery

Persist the active step index and nonce with the local claim. After daemon restart, inspect the container, resume log upload, replay any pending conclusion, then reconcile the server cursor.

Protocol break

Bump RUNNER_PROTOCOL_VERSION directly to V3. Older runners become disabled until upgraded; add no compatibility adapter.

Server authority

Step start/finish calls are idempotent and validated against the current attempt, token, workflow revision, and prior step states.

Do not infer state from log markers

The current ==> and <== lines can remain friendly output, but they cannot determine persisted step state. Control events and user output require separate channels.

07

Storage and transport

The schema remains normalized and the API separates stable run metadata from potentially large, cursor-based logs. 

CREATE TABLE scope_run_attempt_steps (
  attempt_id         varchar NOT NULL,
  step_index         integer NOT NULL,
  state              varchar NOT NULL,
  started_at_unix    bigint,
  completed_at_unix  bigint,
  exit_code          integer,
  PRIMARY KEY (attempt_id, step_index),
  FOREIGN KEY (attempt_id)
    REFERENCES scope_run_attempts(id) ON DELETE CASCADE,
  CHECK (step_index >= 0),
  CHECK (state IN (
    'pending', 'running', 'succeeded', 'failed',
    'canceled', 'lost', 'skipped'
  ))
);

ALTER TABLE scope_run_logs
  ADD COLUMN step_index integer NOT NULL,
  ADD FOREIGN KEY (attempt_id, step_index)
    REFERENCES scope_run_attempt_steps(attempt_id, step_index)
    ON DELETE CASCADE;

Run detail

GET /repos/:owner/:repo/runs/:run returns run metadata, attempts, steps, runner identity, and terminal reason.

Attempt ordering

Persistence returns at most the run’s 100 durable attempts by created_at_unix DESC, number DESC; the internal number breaks ties but is never shown in the UI.

Step logs

GET .../attempts/:attempt/steps/:index/logs?after= returns bounded incremental chunks and truncation state.

Runner transitions

Start and complete endpoints identify the step index; log append requests include the same index.

List response

The Runs list remains lightweight. It needs only the run summary and a stable detail URL.

Retention

Terminal-run pruning deletes step rows and logs transactionally before releasing retained workflow/source objects.

08

Staged delivery

Land the source of truth before its consumers. Each stage has a usable exit gate and removes the superseded path rather than leaving parallel models.

Stage 1

Step execution domain

Add states, terminal reasons, transition behavior, attempt aggregation, and invariant tests.

  • Materialize steps from the pinned workflow revision on claim.
  • Define success, failure, cancellation, timeout, loss, and skipped behavior.
  • Preserve retry isolation and immutable history.
Exit gate: domain tests prove no out-of-order start or inconsistent aggregate result is representable.
Stage 2

Destructive persistence update

Add step entities, constraints, queries, log association, and retention cleanup.

  • Update the canonical schema directly; do not add compatibility columns or migration shims.
  • Lock attempt and step transitions in one transaction.
  • Return attempts in newest-first order from persistence.
Exit gate: database tests cover claim, transition idempotency, retry isolation, ordering, and pruning.
Stage 3

Runner protocol and recovery

Move execution to sequential container restarts, report step events, and bump the runner protocol.

  • Retain one bounded container and immutable source/image behavior.
  • Gate user code behind a nonce-authenticated, durable step-start handshake.
  • Upload logs with their step index.
  • Reconcile active-step journal state after runner restarts.
Exit gate: a killed and restarted daemon resumes the active step without duplicating state or logs.
Stage 4

Repository detail API

Expose attempts, steps, runner identity, typed reasons, durations, and cursor-based step logs.

  • Preserve member-only access and not-found behavior across repositories.
  • Keep list payloads small and detail payloads bounded.
  • Regenerate the TypeScript contract from Rust exports.
Exit gate: workflow tests prove authorization, newest-first ordering, log isolation, and terminal detail.
Stage 5

Dedicated run-detail route

Replace accordion logs as the primary experience with a shareable route and the flat attempt/step layout.

  • Open the newest attempt by default and preserve the user’s later expansion choices.
  • Poll metadata every two seconds and selected logs incrementally.
  • Keep cancel and Run again behavior scoped to the run.
Exit gate: desktop/mobile browser tests cover direct navigation, refresh, expansion, retry, cancellation, and live completion.
Stage 6

Delete the opaque path

Remove monolithic-script completion assumptions and inline log-only detail behavior.

  • Delete any response fields and helpers made redundant by structured attempts.
  • Keep CLI streaming, but source its terminal result from the new aggregate state.
  • Run full workspace, API, web, runner recovery, and physical UI verification.
Exit gate: there is one authoritative step model and no UI parsing or dual execution path remains.

10

UI states and behavior

Every asynchronous failure stays beside the region that can recover from it. Older attempt history remains visible while the current attempt changes.

Initial loading

Render the repository chrome and run-detail header skeleton; do not flash an empty attempt list.

Queued attempt

Newest row shows queued state, creation time, desired runner, and cancel action. Steps remain pending.

Running attempt

Newest row stays expanded. The running step and its selected log cursor refresh every two seconds.

Terminal attempt

Fetch one final metadata/log update, preserve expansion, and expose Run again.

New retry arrives

Insert the new attempt at the top and expand it. Do not relabel, renumber, or mutate older rows.

Metadata refresh error

Retain last-known attempts, mark them stale, and offer Retry now without clearing selected logs.

Step log error

Keep the selected step open and show retry beside its log panel. Other attempts and steps remain usable.

Accessibility

Rows are real buttons with stable aria-controls; state uses text plus color; coarse targets remain at least 44px.

Verification matrix

The test emphasis is transition correctness and recovery. A polished mockup is not enough if step records can disagree with the attempt.

Claim creates exactly one pending row per immutable workflow step.
Only the first eligible pending step can start.
Duplicate start, log, and completion requests are idempotent.
A failed step records its exit code and skips all later pending steps.
Final-step success concludes the attempt and run atomically.
Cancellation and lease loss conclude the active step consistently.
Retry creates fresh step rows and leaves prior attempts unchanged.
Attempts return newest first under timestamp ties.
No rendered text or accessible name contains an attempt ordinal.
Logs cannot cross attempt or step authorization boundaries.
Runner restart resumes the active step and cursor without duplicate output.
Retention deletes attempt steps before workflow/source release.
Direct run-detail navigation survives refresh and client navigation.
390×844 and 1440×1000 layouts have no page-level horizontal overflow.
Cancel and Run again retain focus and announce local failures.
Full Rust, CLI, API, web, smoke, and physical UI suites pass.
12

Principal risks

Runner and server disagree after a restart

Persist an explicit local active-step journal and make all server transitions idempotent.

User output masquerades as control state

Separate the runner-owned journal from stdout/stderr; never parse friendly log markers.

Aggregate and step states diverge

Conclude steps and attempt/run aggregates inside one locked persistence transaction.

Retries reorder while polling

Use server-owned descending creation/id order and generation guards in the route client.

Detail payload grows without bound

Return bounded metadata and fetch selected step logs incrementally by cursor.

Fresh-shell semantics surprise workflows

Document that files persist but shell-local directory and environment changes do not.
