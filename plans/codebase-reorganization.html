Scope VCS refactor brief · 2026-07-25
Migration sequence Verification
Architecture decision / implementation plan

Replace scope-core. Do not replace it with another catch-all.

The proposed reorganization is valid once it is treated as an ownership migration, not a directory shuffle: domain behavior becomes a dependency-free center; delivery, persistence, storage, and Git mechanics become named adapters; old aliases and compatibility paths disappear.

Decision

Proceed as seven atomic, behavior-preserving checkpoints. Keep every checkpoint green and delete the old path as soon as its consumers move. No API, schema, CLI, or product-behavior changes are part of this plan.

01 / Diagnosis

The shape is confusing because ownership is.

scope-core currently names no coherent boundary. It contains durable rules, HTTP-shaped errors, PostgreSQL persistence, object storage, Clerk verification, environment config, Git segment mechanics, runtime events, clocks, and test scaffolding. The problem is not that these pieces exist; it is that their dependency direction is hidden inside one crate.

Consumers

Outer programs

  • api — Axum, Clerk, SSE, orchestration
  • worker — jobs and compaction
  • cli — intentionally standalone workspace
  • scope-api-contract — wire types and TS export
Current center

scope-core

  • Repository and request behavior
  • ApiError and HTTP taxonomy
  • SeaORM, schema, outbox, cleanup
  • S3, encryption, filesystem storage
  • Git manifests, compaction, object keys
  • Clerk/JWT, env config, clock, broadcast bus
Symptoms

Boundary leaks

  • Domain code returns transport errors
  • Contract re-exports domain compilation features
  • API uses cross-directory #[path] modules
  • Physical object keys live in domain values
  • String event reasons become implicit protocols
02 / Target

Durable rules at the center. Thin, named adapters outside.

The compiler should enforce the architecture. scope-domain owns concepts, invariants, transitions, access policy, projection policy, and required effects. It knows nothing about HTTP, Tokio, Postgres, filesystems, object encryption, Clerk, or TypeScript generation.

Arrows point toward dependencies. The dashed edge is generated TypeScript, not a runtime Rust dependency. API and worker compose adapters; adapters do not call one another through a generic “infrastructure” layer.

03 / Boundary laws

Rules that make the move architectural.

These are exit criteria, not aspirations. A file move that violates any of them does not count as completing the phase.

L01 The domain is a leaf.

No Axum, Tokio, SeaORM, Reqwest, JWT, filesystem, object-store encryption, or ts-rs dependencies.

L02 Errors belong to behaviors.

Repository, request, discussion, credit, and projection failures are domain errors; API status mapping stays in the API.

L03 Effects are declared, not performed.

Domain transitions return explicit required effects. API, worker, and Postgres adapters execute and persist them.

L04 Time and entropy enter as inputs.

Clocks, token generation, hashing, and random codes live outside the domain and feed deterministic transitions.

L05 Wire shapes are contract-owned.

The contract defines serialized DTOs and explicit conversions. It does not broadly re-export domain types.

L06 No compatibility shell.

Update consumers atomically in each phase. Do not retain scope-core aliases, wildcard re-exports, or deprecated paths.

04 / Ownership map

Every current module gets a specific answer.

The highest-risk mistake would be moving each top-level folder wholesale. Several folders contain multiple layers and must be split along behavior and adapter boundaries.

05 / Migration sequence

Seven green checkpoints, each with its own proof.

Do not create every empty crate up front. Each phase introduces only the boundary it can populate, migrates all consumers for that slice, proves behavior, and removes the superseded path.

Phase 0

Freeze the contract

Create evidence that a structural change did not alter the product.

Change

  • Make root CI execute every workspace crate’s own tests; widen Rust and CLI workflow path filters to crates/**.
  • Record the current workspace, standalone CLI, web, API workflow, local-dev, and Git/worker test commands.
  • Capture cargo test -- --list for the API so later test moves cannot silently reduce coverage.
  • Regenerate web/src/api/types.generated.ts and require a clean diff.
  • Capture the current DB schema checksum, route/DTO export output, event JSON, and error-to-HTTP mappings.

Do not change

  • No schema migration, route rename, DTO rename, status-code change, or CLI workspace merge.
  • No top-level apps/ or tools/ move; that is cosmetic churn with deployment cost.
Exit gate: baseline commands are reproducible and generated outputs are clean before extraction starts.
Phase 1

Extract the honest domain

Make core business behavior compile without delivery or infrastructure dependencies.

Change

  • First remove ApiError, time, entropy, and storage-location leakage while code still lives in scope-core; keep this semantic disentangling separately revertible.
  • Then create scope-domain and atomically move repository, request, collaboration, credit, visibility, projection, and pure auth decisions.
  • Split store.rs by behavior; rename infrastructure-flavored entities and preserve aggregate atomicity.
  • Introduce behavior-owned errors and pass time, generated IDs, codes, and token hashes into transitions.
  • Separate stable ContentRef identity from physical object-store location.
  • Update both lockfiles and CLI Railway staging in the same checkpoint as the new path dependency.

Delete while moving

  • Delete domain imports of ApiError, unix_now(), and physical object-key policy.
  • Move AppCatalog to dev/test seed fixtures; delete the trivial app_catalog() alias.
  • Delete speculative ProjectionSource and repo_for_projection_preview until a second source exists.
Exit gate: no duplicate or shim domain tree remains, and scope-domain has no HTTP, async runtime, database, filesystem, object-store, auth-provider, or TypeScript-generation dependency.
Phase 2

Make the contract honest

Separate stable wire compatibility from internal domain representation.

Change

  • Define contract-owned DTOs and serialized enums, including the ownership decision for SessionIdentity.
  • Add explicit From/TryFrom mappings at the API/contract boundary.
  • Keep route metadata and TypeScript export inside scope-api-contract.

Delete while moving

  • Delete broad pub use scope_core::… exports.
  • Delete the domain ts feature and all domain ts-rs derives.
  • Do not add compatibility aliases for old Rust paths.
Exit gate: regenerated TypeScript is byte-identical; route and serialization tests pass; domain compiles with no knowledge of the web contract.
Phase 3

Extract storage and Git mechanics

Name the shared technical capabilities without moving HTTP orchestration into them.

Change

  • Create scope-object-store around the existing trait and S3, encrypted, filesystem, and memory implementations.
  • Create scope-git for manifest codecs, segment-chain mechanics, materialization, storage policy, and compaction.
  • Give each adapter its own error type and map errors at API/worker boundaries.
  • Retain scope-git-process as the narrow leaf used for safe child-process execution.
  • Preserve object-store wrapper order exactly: API budgeted → encrypted → S3; worker encrypted → filesystem/S3.

Delete while moving

  • Delete the misleading unused repository parameter from source-content storage APIs unless namespacing becomes real.
  • Delete duplicated object-key, hashing, and manifest rules from API and worker call sites.
  • Do not move api/src/git wholesale; handlers, auth, state, and response streaming remain delivery code.
Exit gate: API and worker share Git/storage mechanics through explicit crates, with no Axum or AppState dependency outside the API.
Phase 4

Extract Postgres and split events

Make persistence an adapter that loads, invokes, persists, and commits domain behavior.

Change

  • Create scope-postgres for connections, schema, rows, encoders, repositories, transactions, read models, outbox, cleanup, compaction jobs, and notifications.
  • Break MetadataStore into focused capabilities sharing an internal pool.
  • Split semantic domain events, Postgres envelopes/LISTEN/NOTIFY, and API runtime broadcast/SSE state.
  • Replace string change reasons with typed semantic variants.
  • Preserve the notification channel, capacity 128, origin suppression, malformed-payload behavior, and two-second reconnect loop until a separate behavior change is approved.

Delete while moving

  • Delete database response shaping and any reimplementation of authorization or lifecycle rules.
  • Delete the mixed repo_events.rs module once all three owners exist.
  • Delete shared clock calls from transactions; accept explicit now from orchestration.
Exit gate: schema is unchanged; transaction and workflow suites pass; Postgres does not depend on HTTP contracts or object storage.
Phase 5

Thin the binaries

Leave API and worker as explicit composition, orchestration, delivery, and error-mapping layers.

Change

  • Keep AppState as dependencies/bootstrap; extract push intents, repo access, repo changes, cleanup orchestration, and cache reaping into behavior-owned API modules.
  • Move Clerk verification and auth issuance services under API auth; split API and worker settings beside their binaries.
  • Move dev API code under api/src/dev and private workflow tests under api/src/workflow_tests.
  • Preserve AppState::from_env startup ordering and update the worker tracing filter when the old crate target disappears.

Delete while moving

  • Delete cross-directory production #[path] tricks, wildcard persistence aliases, and API-level core re-exports.
  • Keep ordinary sibling *_tests.rs path modules; they are not an architecture leak.
  • Do not expose private internals just to turn internal workflow tests into integration tests.
Exit gate: delivery modules translate inputs, invoke behavior, coordinate adapters, and translate outputs—without defining new product rules.
Phase 6

Reap the old shell

Finish the migration instead of preserving a second architecture indefinitely.

Change

  • Remove the final old workspace, CI, Railpack, and CLI staging references; path changes for earlier extracted crates must already have landed atomically with those crates.
  • Keep the CLI excluded with its own lockfile and run its checks through --manifest-path.
  • Run repository-wide searches for old crate names, re-exports, path tricks, and stale docs outside the protected root README.

Delete

  • Delete crates/scope-core, its features, and every compatibility re-export.
  • Delete empty forwarding modules and duplicated tests made obsolete by compiler-enforced boundaries.
  • Delete only proven dead code; retain platform artifacts and intentionally separate deployment surfaces.
Exit gate: rg "scope_core|scope-core" finds no live code or build references, all delivery pipelines are green, and the old crate is absent.
06 / Code-reaper ledger

Subtract aggressively, but only with evidence.

Pre-alpha status removes the need for compatibility scaffolding. It does not justify deleting code merely because its purpose is easy to miss. The ledger distinguishes architectural residue from earned boundaries and unrelated churn.

Delete

Proven duplication, forwarding, or mixed ownership replaced during the migration.

  • scope-core and compatibility re-exports
  • Shared ApiError and shared config/persistence modules
  • Domain ts-rs features and contract re-exports
  • Cross-directory production path inclusions
  • Trivial catalog/projection aliases and unused parameters

Keep

Mechanisms with one demonstrated owner or product rules that belong in the durable center.

  • scope-git-process as a bounded runner
  • Repository aggregate atomicity
  • Projection and visibility policy in domain
  • Explicit RepoEffect-style side effects
  • CLI’s separate workspace and lockfile

Defer

Changes that do not improve ownership enough to justify coupling them to this refactor.

  • Moving binaries under a new apps/ tree
  • Moving scripts into a new tools/ tree
  • Database schema redesign
  • API route or response redesign
  • A generic application, infrastructure, or auth crate
07 / Verification

Prove structure and behavior separately.

Every phase runs the smallest relevant checks immediately, then the full matrix before merge. Dependency tests are listed explicitly because testing a consumer does not automatically execute every dependency crate’s own test suite.

1 / Compile law

Domain manifest and dependency tree show an inward-only center.

2 / Unit law

Each moved behavior keeps focused regression tests beside its owner.

3 / Workflow law

API, local-dev, Git, worker, cleanup, outbox, and auth flows remain green.

4 / Contract law

Generated TypeScript and schema have no unintended diff.

5 / Product law

Web check/build and seeded browser smoke prove the integrated surface.

08 / Risk controls

The dangerous parts are semantic seams, not file moves.

The plan stays reviewable by making ownership decisions before path rewrites and by prohibiting schema or behavior redesign inside structural phases.

Error mapping

Map each behavior error exhaustively to the current status and payload; snapshot or route-test the mapping before removing ApiError.

Session identity

Decide its semantic owner explicitly. Contract, CLI-session persistence, and API auth all consume it; a blind import rewrite will recreate the coupling.

Content references

Separate stable SHA/Git identity from physical object keys before extraction, then verify deduplication, encrypted reads, cleanup, and compaction.

Aggregate hydration

Do not fragment the repository aggregate to mirror tables. Postgres can use focused repositories while hydrating the complete behavior-owned state.

Event delivery

Keep semantic events, durable Postgres envelopes, and transient SSE connection state distinct; test reconnect, lag, and notification fan-out.

Deployment paths

Update CI package lists and CLI staging copies in the phase that deletes old crates. Root workspace checks alone will not cover the standalone CLI.

Done means the architecture is visible in the dependency graph.

  • scope-domain is infrastructure-free and owns product policy.
  • API and worker coordinate named adapters without inventing rules.
  • Contract DTOs are explicit and generated TypeScript is unchanged.
  • Postgres owns schema, transactions, jobs, and notifications only.
  • Object storage and Git use adapter-native errors.
  • scope-git-process remains small and single-purpose.
  • The CLI remains standalone and passes its separate pipeline.
  • No scope-core, forwarding aliases, or legacy paths remain.
  • No database schema, API, CLI, or product behavior changed accidentally.
  • Full Rust, web, contract, workflow, and browser checks are green.
