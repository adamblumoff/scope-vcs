Git projections · public requests · commit identity

Keep the existing flow. Preserve the contributor’s actual commits.

Scope already lets a contributor clone the public projection, push a public request, and merge it into the complete private repository. This plan changes only the final projection step: after merge, public main should reuse the contributor’s original Git objects instead of replacing them with one Scope-generated commit.

Recommended decision

Store explicit request provenance in durable domain history, reuse the request’s native commit range when building the public projection, and fail closed whenever ancestry or projected-tree equivalence cannot be proven.

01 · Outcome

One behavioral difference

The request, review, permissions, privacy checks, canonical merge, and settlement remain intact. Only the public projection’s post-merge Git ancestry changes.

Today

The canonical merge contains the native request commits, but the projection layer ignores them and creates a new synthetic public commit.

Target

The canonical merge stays the same. The projection layer recognizes the public-request origin and advances public main through the already-stored native commits.

Scope-generated projection commit exact contributor commit canonical private merge

Two materialization paths

Native preservation is intentionally narrow. A fully public request can keep its exact Git objects because nothing must be removed. A canonical commit that mixes public and private changes must be rewritten because filtering out the private half changes the tree and therefore the SHA.

Rule: preserve exact Git identity only when the complete commit is already safe to publish; otherwise generate a sanitized public projection commit.

02 · Contract

Invariants before code

These rules belong in scope-domain. The API and Git adapters should gather evidence, call domain behavior, materialize the result, and surface failures without inventing alternate semantics.

1
Canonical remains complete

Canonical main keeps the full private tree and a Scope merge commit whose second parent is the exact public request head.

2
Native means byte-for-byte native

A preserved public commit keeps its SHA, parents, tree, message, author, timestamps, optional signature, and other headers.

3
No private object becomes reachable

Every reused commit must already descend from public main and its tree must equal the expected projected public tree at that point.

4
Append-only history gets stable SHAs

If the public base remains valid, merged request commits remain reachable from public main permanently.

5
Failure is explicit

Stale ancestry, changed visibility, missing objects, or a tree mismatch blocks the merge. There is no silent masking or synthetic fallback.

6
The ordinary flow does not change

Contributors still clone public main, push named request branches, and wait for maintainer review. Direct public-main pushes remain prohibited.

03 · Architecture

Carry origin through the system

The contributor objects are not missing: the canonical merge already retains them as its second-parent chain. The missing information is durable intent—today the domain flattens a request merge into one anonymous logical update.

04 · Domain model

Represent why a commit exists

Keep file content and visibility in the existing source graph. Add only the provenance needed to choose safe materialization. Do not introduce a second authoritative public-content store or duplicate request snapshots.

    Generate,
    PreserveGitCommit { oid: String },

pub struct ProjectedCommit {
    // existing logical identity, author, message, changes...
    materialization: ProjectionMaterialization,
}
One source of content truth

SourceGraph and visibility events continue to determine the projected tree.

One source of Git provenance

The logical commit origin says whether a public commit may reuse a native object.

No snapshot duplication

Native objects are loaded from the canonical raw Git manifest, where the merge already makes them reachable.

No optional legacy field

Origin is required for every new logical commit. Pre-alpha data and schema are replaced destructively.

Domain decides eligibility

The outer Git layer verifies objects and trees; it does not decide whether silent rewriting is acceptable.

05 · Merge path

Validate, merge, verify, persist

Preparation may perform Git work, but no durable state changes until both canonical merge construction and public projection verification succeed.

08 · Deletion

Subtract the conflicting behavior

Preserving an exact commit and silently changing its tree are mutually exclusive. Remove the alternate semantics instead of retaining hidden fallbacks or compatibility modes.

Delete
current_policy_public_request_head

It can replace the contributor head with a policy-masked synthetic commit. The new contract rejects a request when current policy makes any touched path private.

Delete
restore_index_path_from_tree and masking index machinery

These helpers exist only to construct the silently altered request commit. Removing the behavior should remove its files, imports, temporary index, branches, and tests.

Replace
anonymous rv_merge_* construction

Do not keep a parallel legacy route. Request merges must enter the domain with explicit origin facts; normal main pushes retain their own explicit origin.

Reject
silent synthetic fallback on native verification failure

Missing objects, parent mismatch, or projected-tree mismatch indicate corruption or an unmodeled rewrite. Failing closed is simpler and safer than publishing a different history.

Avoid
a new public-content ledger or copied request snapshot

The canonical source graph owns content and the canonical Git merge already owns native objects. Only provenance facts are new.

Delete
unused projection and history abstractions

Remove the unused Policy argument from project_graph. Verify and remove AuthorVisibility and logical parent_ids if production has no behavior that consumes them; do not preserve test-only concepts.

Replace
fake pv_* identities in public history

Public history must return the real materialized Git OID and parents. Consolidate or delete hand-built history identity and preview-head hashing that can disagree with the repository users clone.

Extract
projection materialization from broad upload.rs

Move generated/native commit construction, tree verification, and projection-cache assembly into a behavior-owned module. Keep protocol authorization and response handling thin.

No compatibility
nullable origin, serde defaults, backfill, dual cache semantics

Reset pre-alpha state and bump projection cache semantics. One new model should exist after the change.

09 · Verification

Prove identity and privacy together

A SHA-preservation test without a privacy reachability test is incomplete. A tree-equality test without a real clone/fetch test can miss Git transport and cache bugs.

Domain

  • Public request origin produces native materialization only in the public view.
  • Private view remains generated because its parent and tree include private content.
  • Mixed or newly private request changes are ineligible and return a domain conflict.
  • Later generated public commits attach after a preserved native head.
  • Cache identity changes when origin, base, head, or materialization kind changes.

Git workflow

  • Multi-commit request preserves every SHA, parent, message, author, timestamp, and signature header.
  • After merge, git merge-base --is-ancestor request_head public/main succeeds.
  • Canonical main remains a different merge SHA and retains private files.
  • A private-only canonical advance does not stale the public request.
  • A public-main advance blocks until the request includes the new public head.

Security and durability

  • git rev-list --objects --all in the public repo contains no private blob or path.
  • Request path made private before merge is rejected, never masked.
  • Missing native object, parent mismatch, or tree mismatch aborts without settlement.
  • Cold cache and process restart rebuild the identical public head.
  • git fsck --full passes for canonical and public repositories.
10 · Risks

Sharp edges to resolve deliberately

The primary risk is not preserving the wrong metadata; it is accidentally making a private object reachable while attempting to reuse a commit.

RiskSeverityMitigation
Native request commit contains an unexpected private blob or parent. High Keep push-time safety checks, revalidate at merge, compare every native tree with the domain-derived projected tree, then scan public reachability.
Public main advances while a request is under review. Medium Require the current public head in request ancestry. V1 can ask the contributor to merge current public main and push the resulting fast-forward update.
A later visibility rewrite changes already-published history. High Make destructive public-history rewrite a separate explicit operation with a new projection generation. Never pretend previously cloned content became secret again.
Projection cache serves a synthetic history after origin semantics change. Medium Bump cache semantics and hash materialization kind, native base, ordered commit OIDs, and head into the key.
History API and Git clone disagree about commit granularity. Medium Expose preserved request commits as individual projected commits or explicitly defer the history API until it can represent the native range accurately; do not report a false synthetic SHA.

Stale request updates

Recommendation for V1: require the contributor to merge current public main into the request, which remains a normal fast-forward branch push. Supporting rebases requires deliberate force-with-lease semantics because request refs currently reject non-fast-forward updates.

Destructive public rewrites

Recommendation: exclude rewrite/redaction from this implementation. Preserve SHAs for append-only public history and make any later rewrite an explicit generation-reset design, never an automatic fallback.

11 · Done

Acceptance criteria

The change is complete when a contributor can observe ordinary Git merge semantics without weakening Scope’s private/public boundary.

Existing clone → public request → maintainer review → canonical merge flow still works.
Public main reaches the exact request head after a successful public merge.
Contributor commit identities, metadata, and signature headers survive unchanged.
Canonical main remains complete, private, and separately identifiable.
Private-only canonical work does not invalidate an otherwise current public request.
Changed public ancestry or visibility produces an actionable conflict before persistence.
No silent masking, synthetic fallback, legacy origin, or compatibility branch remains.
Domain, Postgres, Git workflow, privacy, restart, cache, and fsck tests pass.
