Source control with boundaries

Open the project.
Keep control.

Scope gives maintainers one repository that can present different views to different people—without splitting the project or surrendering control of the code and the attention around it.

One source · permissioned projections
publicprivate
No repository split

Public and private work stay in the same project instead of drifting across synchronized repositories.

No accidental authority

No hidden rules

Trusted repository guidance travels with contributor workspaces and their coding agents.

01 / boundaries

Protect the code and the attention around it.

A

The code boundary

Maintainers decide which files are public and which remain private. Outside collaboration happens against a safe projection, not an all-or-nothing clone of the repository.

B

The attention boundary

Contributors work privately in Draft and submit once they want review. Maintainers receive intentional work, while discussions and revisions remain attached to one request.

02 / requests

A small lifecycle with nowhere to hide ambiguity.

Draft

Participants shape the change privately without placing it in the maintainer queue.

Open

The author submits once. The request stays mutable while review and revisions continue.

Merged

Accepted work enters the repository with its discussion and history intact.

Closed

Work can end clearly without pretending every contribution belongs in the project.

What exists today

A deliberately small foundation.

Scope is early and experimental. The product is proving the collaboration loop before adding economies, automated qualification, or speculative platform machinery.

The direction

Open source on the maintainer’s terms.

Agentic coding makes patches cheap and human attention expensive. Scope is building source control where maintainers define what is visible, how work enters, and what deserves the project’s time.
